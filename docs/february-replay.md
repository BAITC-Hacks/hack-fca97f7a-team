# Февральский прогноз: интерфейс и воспроизводимость

Основной режим Samal воспроизводит расчёты за **1–28 февраля 2026 года**.
Выберите турбину T1/T2, день назначения и горизонт 24/48 часов. Для 1 февраля
момент расчёта — 31 января 23:00 Asia/Almaty (18:00 UTC); для 2 февраля —
1 февраля, далее ежедневно. Первый целевой час — местная полночь выбранного дня.
Всего 28 origins с 31 января по 27 февраля, по две турбины.

56 запусков по 48 часов дают 2 688 строк. Последний запуск выходит в 1 марта.
Непрерывный февральский ряд берёт первые 24 часа каждого запуска: 1 344 строки,
ровно 672 часа на турбину. CSV хранит UTC; границы февраля определяются по
Asia/Almaty (UTC+5). Мощность нормализована [0,1], не МВт/МВт·ч.

## Что видно в интерфейсе

Дата расчёта, выпуск погоды, источник и статус доступности сопровождают график,
таблицу и оба CSV. Дата назначения не является датой инициализации погоды.
Смена дня воспроизводит новое решение, очищая прежний результат и разговор.
Объяснение и чат получают серверный forecast ID и используют численные значения
именно этого расчёта. Текущий прогноз остаётся отдельным режимом.

`POST /api/replay/forecasts` принимает `turbine_id`, `forecast_date`,
`horizon_hours`, `weather_source`. В HTTP основной источник задаётся как `weather_source="verified"`; он
использует операционный архив. В CLI тот же адаптер выбирается флагом
`--weather-source operational`.
Сервер читает проверенный архив, пишет канонический CSV и передаёт этот файл
модели. Отсутствующий/повреждённый архив приводит к ошибке: текущая или фактическая
погода не подставляется. Обучение внутри HTTP-запроса не выполняется.

## Основной источник: операционный архив ECMWF

Используются операционные прогнозы IFS из официального публичного ECMWF Open Data,
включая реплику `https://storage.googleapis.com/ecmwf-open-data`.
[Документация ECMWF](https://www.ecmwf.int/en/forecasts/datasets/open-data)
описывает открытые операционные данные и доступные облачные копии.
[Реестр AWS](https://registry.opendata.aws/ecmwf-forecasts/) отдельно подтверждает
операционный характер реплики и управление ECMWF.

Проверка выполняется для **каждого использованного объекта**: путь и инициализация
выпуска, серверная дата объекта не позднее origin, идентичность при скачивании,
хеши GRIB-сообщений, параметры и целевые сроки. Серверное время сохранения объекта
— свидетельство доступности в реплике; оно не выдаётся за точное время первой
публикации ECMWF. Сегодняшнее время скачивания записывается отдельно.
Доверенная основа проверки — официальный архив и его серверные метаданные.

Кеш задаётся `OPERATIONAL_WEATHER_DIR` (по умолчанию каталог
`operational_weather` внутри `ARTIFACT_DIR`). Для origin 18 UTC используется
операционный выпуск того же дня 00 UTC: исходные сроки 18–66 часов с шагом 3 часа
покрывают все цели 19–66 часов. `available_at` — максимальный `Last-Modified`
всех использованных индексов и объектов GRIB, а
`availability_basis=operational_object_last_modified`. Только после проверки
хешей и хронологии результат получает `provenance_status=verified`.

Сетка источника — 0,25°. Вход включает температуру `2t` и компоненты ветра `10u`,
`10v`, преобразованные в °C и скорость м/с. Выбор ближайшей точки сетки и
линейная интерполяция компонент u/v и температуры с трёхчасовых сроков
до почасовых значений отражаются в provenance. Скорость вычисляется из
интерполированных компонент.
Интерполяция использует только один доступный выпуск, без будущих наблюдений.
Разрешение и подготовка отличаются от Open-Meteo, использованного при обучении:
проверенное происхождение погоды само по себе не доказывает качество мощности.

## Полный операционный прогон

С подготовленными моделями (быстрый запуск из комплекта — в [README](../README.md)):

```sh
python -m scripts.fetch_operational_weather
python -m scripts.replay --weather-source operational --output-dir artifacts/february_operational
python -m scripts.audit_february --report-dir artifacts/february_operational > artifacts/february_operational/audit.json
```

Сначала загружается и проверяется архив. Затем replay использует локальные входы,
пишет CSV и выполняет инференс без переобучения/LLM. Полнота всех 56 запусков и
историческая доступность проверяются по `artifacts/february_operational/report.json`.
До завершения этого прогона нельзя заменять итоговый отчёт проверкой одного дня.

## Прежний условный комплект Open-Meteo

[deliverables/february_2026](../deliverables/february_2026/README.md) содержит
предыдущий расчёт: 56 запусков, 2 688 строк на 48 часов, 1 344 строки непрерывного
февраля и переносимый ZIP с двумя моделями. Он использует Single Runs с отдельным
статусом `provider_documented`, `available_at=null`, `availability_verified=false`.
Предполагаемая доступность — выпуск +24 часа; для origin 18 UTC выбран выпуск
00 UTC предыдущего дня, возрастом 42 часа. Это допущение, не журнал публикации.

Для явного повторения именно старого условного варианта:

```sh
python -m scripts.fetch_replay_weather
python -m scripts.replay --weather-source provider-documented --output-dir artifacts/february_conditional
```

Его нельзя переименовать в verified или выдавать за новый операционный результат.
Строгий архивный режим с внешним свидетельством тоже сохраняется отдельно.
Описание [Single Runs](https://open-meteo.com/en/docs/single-runs-api) и
[пояснение провайдера](https://openmeteo.substack.com/p/single-runs-api)
не служат точным временем публикации каждого конкретного выпуска.

## Данные и точность

Модели заморожены на завершённых часах до `2026-01-31T18:00:00Z`.
Февральские цели не использовались для обучения или выбора модели. Исходные T1/T2
заканчиваются 31 января несмотря на имена файлов. Дополнительный комплект
материалов также не содержит фактической февральской мощности.
Поэтому февральские MAE/RMSE не вычисляются. Диагностика в
[FORECASTING_REPORT.md](../FORECASTING_REPORT.md) не оценивает точность этих
февральских прогнозов. Временные границы SCADA и нормировку ещё следует уточнить
у владельца данных.
