# Интеграция данных, погоды, модели и интерфейса

Рабочий интерфейс проекта — React + FastAPI. Точные маршруты, DTO, Python-сигнатуры и CSV-схема описаны в [CONTRACTS.md](CONTRACTS.md); он является основным контрактом. [README.md](README.md) содержит команды запуска и сценарий демо, а [DATA_MODEL_HANDOFF.md](DATA_MODEL_HANDOFF.md) — аудит исходных измерений и соглашение о признаках. Этот документ поясняет связь компонентов и оставшиеся условия интеграции.

```text
React → FastAPI api.py → agent.run_forecast
                          ├─ weather.fetch_weather: UTC часы, м/с, °C, provenance
                          ├─ model_input.write_model_input: точный CSV и SHA-256
                          └─ model.predict_power_csv: проверка CSV и прогноз
      ← числовой прогноз, анализ, происхождение, trace, ID
React → api.py → explanation.py: объяснение сохранённого прогноза
```

`data.py` отдельно читает реальные измерения T1/T2 и формирует полные UTC-часы. `scripts/train.py` обучает и сохраняет отдельную модель каждой турбины. Обучение выполняется через CLI; HTTP-запросы его не запускают. Две регрессии используют `[wind_speed_ms, temperature_c]`, а результат — нормализованная мощность `[0,1]`. Модель читает именно скачиваемый CSV `weather-features-v1`, содержащий `turbine_id,valid_at,wind_speed_ms,temperature_c`; CSV не содержит целевых значений мощности.

Текущая погода — явно синтетические сохранённые запуски, координаты условные. `archive` не работает без проверенных координат и погодного прогноза, который был выпущен и доступен до `origin`. Живая интеграция OpenAI существует, но при отсутствии ключа/ошибке возвращает обозначенное расчётное объяснение. Числовой прогноз от LLM не зависит. Все пользовательские сообщения и доступные подписи должны быть русскими; API-идентификаторы и CSV-заголовки сохраняются.

## Соглашение о погодных признаках

Тренировочный ветер — средняя скорость из турбинных CSV в м/с; температура — средняя температура окружающей среды в °C. Источники усредняются по шести полным десятиминутным интервалам на UTC-час. Вход прогноза — погодный час с началом `origin+1h` ... `origin+24/48h`. Порядок признаков одинаков для обучения и инференса. Высота измеренного ветра неизвестна; текущий `weather.py` не указывает высоту прогнозного ветра. Пока оба метаданных не подтверждены, перевод высоты ветра и утверждение о физической эквивалентности недопустимы. Оценка регрессора на измеренной погоде отличается от качества итогового прогноза на погоде из API.

Адаптер реального провайдера должен установить `initialized_at <= available_at <= origin`, подтвердить один run с полным часовым покрытием, известные единицы и высоту ветра, а также сохранить источник и контрольную сумму. Фактическая погода, реанализ или прогноз, опубликованный после origin, не заменяют архивный operational/as-issued прогноз. Неполный или недостоверный набор приводит к явной ошибке до кэша и инференса. Координаты на карте выбирают только зарегистрированные T1/T2.

## Проверка совместимости

Из корня репозитория после установки зависимостей и обучения:

```sh
python -m pytest -q
npm --prefix frontend run build
```

Для совместной проверки запустить `python -m uvicorn api:app --host 127.0.0.1 --port 8000`, выбрать обе турбины и горизонты 24/48 часа, скачать входной CSV, проверить число строк, порядок UTC-времени, источник погоды и отсутствие устаревшего результата после смены параметров. Автотесты не используют платные вызовы. Метрики и границы их интерпретации приведены в [EVALUATION_REPORT.md](EVALUATION_REPORT.md).

Работа по потокам: A подтверждает координаты/погодный архив и поддерживает `agent.py`, `weather.py`, `api.py` и общие контракты; B отвечает за данные, CSV и модель; C — за русский интерфейс и объяснения. Изменение общей CSV-схемы требует одновременного обновления адаптера, валидатора, модели, DTO и тестов. Полный февральский replay зависит от доказанной архивной доступности, а оценка февраля — ещё и от отсутствующей сейчас истины.
