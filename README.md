# Прогноз мощности ВЭС

Русскоязычная демо-система для двух турбин. Основной сценарий воспроизводит февраль 2026: выберите T1/T2, день 1–28 февраля и горизонт 24/48 часов. Сервер берёт отдельный исторический выпуск погоды, записывает входной CSV, замороженная модель читает этот файл и выдаёт почасовую нормализованную мощность. Результат виден на графике и в таблице; анализ и чат используют тот же сохранённый прогноз. Текущий прогноз доступен отдельным режимом.

Историческая доступность выпусков в готовом комплекте **предполагается**, а не подтверждена для каждого выпуска: это обозначено в интерфейсе и CSV. Полное покрытие февраля не означает доказанного полного соответствия условию жюри. Фактической мощности за февраль в исходных данных нет.

## Запуск

Нужны Python 3.12+ и Node.js 22+. Команды выполняются из корня репозитория:

```sh
python -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements.txt
npm --prefix frontend ci
npm --prefix frontend run build
python -m uvicorn backend.api:app --host 127.0.0.1 --port 8000
```

Откройте <http://localhost:8000>. Swagger: <http://localhost:8000/docs>. Для разработки интерфейса оставьте FastAPI запущенным и отдельно выполните `npm --prefix frontend run dev`; Vite откроется на <http://localhost:5173> и передаст `/api` серверу.

Для февральского демо готовый комплект моделей и 56 погодных ответов уже находится в репозитории. После установки зависимостей распакуйте его и запустите сервер с этими артефактами:

```sh
python -m zipfile -e deliverables/february_2026/replay_bundle.zip artifacts/february_bundle
ARTIFACT_DIR="$PWD/artifacts/february_bundle/artifacts" REPLAY_WEATHER_DIR="$PWD/artifacts/february_bundle/artifacts/replay_weather" python -m uvicorn backend.api:app --host 127.0.0.1 --port 8000
```

Этот запуск заменяет обычную команду uvicorn выше. Расчёт по готовому кешу не требует сети, обучения или OpenAI. Используйте совместимые Python/scikit-learn из `bundle_manifest.json` (комплект создан на Python 3.14). При отсутствии или повреждении артефактов сервер выдаёт ошибку, не подменяет исторический прогноз сегодняшней погодой.

Чтобы подготовить модели с нуля:

```sh
python -m scripts.fetch_training_weather --start-date 2024-01-01 --end-date 2026-01-31
python -m scripts.train_forecast --activate
python -m scripts.fetch_replay_weather
```

Обучение выполняется через CLI, не в запросе. Оно использует только завершённые часы до `2026-01-31T18:00:00Z`; февральские цели не используются. Исходные CSV в `data/` не изменяются. Первичная подготовка требует сети и времени; повторный расчёт читает проверенный локальный кеш.

Объяснение OpenAI необязательно. Скопируйте `.env.example` в `.env` и задайте `OPENAI_API_KEY` на сервере, если хотите включить его. При отсутствии ключа или ошибке провайдера приложение показывает явно обозначенное расчётное объяснение. Ключ не передаётся в React. Автоматические тесты не вызывают платный API.

## Сценарий показа

1. Выберите февральский режим, T1, 1 февраля и 48 часов. Сформируйте прогноз: момент расчёта — 31 января, 23:00 Asia/Almaty; первый целевой час — 1 февраля, 00:00.
2. Покажите дату расчёта, инициализацию погодного выпуска и отметку предполагаемой доступности. Для origin 31 января 18:00 UTC используется выпуск 30 января 00:00 UTC, а не фактическая погода февраля.
3. Покажите график мощности и ветра, почасовую таблицу и точный входной CSV, прочитанный моделью. Мощность нормализована 0–1, не МВт/МВт·ч.
4. Запросите анализ и задайте «Найди лучшие четыре часа подряд», затем «А какой там ветер?». Ответы используют выбранный исторический прогноз.
5. Перейдите к 2 февраля: новый момент расчёта — 1 февраля. Повторите для T2 и 24 часов; смена параметров очищает прежний результат и разговор.
6. Выберите 28 февраля. При 48 часах результат включает 1 марта; месячный CSV содержит только первые 24 часа каждого ежедневного запуска и ровно 672 часа февраля на турбину.
7. Перезагрузите страницу и откройте сохранённый результат без повторного запроса внешней погоды/LLM. При желании переключитесь на отдельный текущий прогноз и обновите погоду.

Готовые месячные CSV и отчёт: [deliverables/february_2026](deliverables/february_2026/README.md).

## Устройство проекта

| Путь | Ответственность |
|---|---|
| `frontend/src/` | React, карта, график, таблица, чат и единый HTTP-клиент |
| `backend/api.py` | FastAPI, проверка запросов, хранение результатов, скачивание CSV |
| `backend/services/agent.py` | Последовательность погода → CSV → модель → анализ |
| `backend/adapters/weather.py`, `replay_weather.py` | Текущая/строгая архивная погода и проверенный кеш отдельных исторических выпусков |
| `backend/ml/model_input.py`, `backend/ml/model.py` | Проверяемый входной CSV и отдельные модели T1/T2 |
| `backend/adapters/forecast_store.py` | Проверяемое локальное хранение прогнозов |
| `backend/adapters/explanation.py` | Объяснение OpenAI и расчётный резервный ответ |
| `backend/core/contracts.py` | Общие схемы, единицы и ошибки |
| `scripts/` | Подготовка данных, обучение, диагностика; вне HTTP-запроса |
| `legacy/` | Старый прототип Streamlit; в активном сценарии не участвует |

Основной поток: `frontend/src/api.ts` → `backend/api.py` → `backend/services/agent.py` → погода → `artifacts/model_inputs/<sha256>.csv` → модель → результат. Объяснение и вопросы запрашиваются по ID сохранённого результата; текстовая модель не меняет числовые предсказания. Погода кешируется пять минут; прогнозы сохраняются локально с контрольной суммой (до 256 файлов, максимум семь дней). Сервер рассчитан на один процесс. Формат API и CSV описан в [CONTRACTS.md](CONTRACTS.md), модель и ограничения проверки — в [FORECASTING_REPORT.md](FORECASTING_REPORT.md).

## Данные, проверка и границы результата

В `data/` лежат раздельные истории T1 (142 360 строк) и T2 (149 499 строк), заканчивающиеся 31 января 2026 года. Модель использует только завершённые часы до `2026-01-31T18:00:00Z`. Погода для текущего прогноза — открытый Open-Meteo ECMWF IFS по координатам турбин, предоставленным пользователем. Ветер API на высоте 10 м; высота датчиков и нормировочный знаменатель мощности неизвестны. Сведения о подготовке данных: [DATA_MODEL_HANDOFF.md](DATA_MODEL_HANDOFF.md).

Для тестов на свежем клоне подготовьте внутренние fixtures и измерительный профиль модели
(в пользовательском интерфейсе эти данные не используются):

```sh
python -m scripts.make_fixtures
python -m scripts.train --mode fixture
python -m pytest -q
npm --prefix frontend run build
```

Сборка React прошла. При интеграции чата 213 тестов прошли; одна ошибка числового форматирования исправлена и проверена отдельным прогоном тестов объяснения. После переноса проверены настоящие запросы Open-Meteo для T1/T2 × 24/48 часов, оба CSV и расчётное объяснение. Chromium с моками API подтвердил работу интерфейса 390/1280 px, выгрузок, обновления, ошибок и защиты от запоздалых ответов. Ранее проверено чтение сохранённого прогноза после перезапуска; это проверка работоспособности, а не точности 24/48-часового прогноза.

Основной сценарий показывает **исторический февральский прогноз**. Готовый
полный расчёт содержит 56 запусков, 2 688 строк на 48 часов и отдельный
непрерывный ряд из 1 344 строк на февраль. Использованы отдельные выпуски
ECMWF IFS, сохранённые локально. Доступность каждого выпуска предполагается
по явно указанному правилу задержки; не выдаётся за доказанное время публикации.
Февральской фактической мощности для оценки ошибки нет.

## Диалог по прогнозу

Пример: «Найди лучшие четыре часа подряд» → «А какой там ветер?» →
«Сравни со следующими четырьмя часами». Сервер сохраняет выбранный период
и историю диалога. Средние, лучшие часы и сравнения вычисляет Python;
LLM формулирует ответ. Таблицы расчётов и ограничения показаны отдельно.
При смене прогноза начинается новый разговор. Без OpenAI доступны расчётные
ответы на типовые вопросы; произвольный разговор требует настроенного LLM.
