# Задачи команды: демо прогноза мощности ВЭС

Цель: пользователь выбирает турбину → получает прогноз погоды → сервер создаёт
CSV → модель читает CSV и прогнозирует мощность → пользователь видит таблицу,
график и объяснение на русском языке → задаёт вопросы по этому прогнозу.

В команде три разработчика: A — backend и погода, B — данные и модель,
C — frontend и объяснения. Имена можно подставить вместо букв.
Контракты модулей: [CONTRACTS.md](CONTRACTS.md). Запуск: [README.md](README.md).

## Что уже реализовано

- [x] React + FastAPI, выбор T1/T2, график и таблица на 24/48 часов.
- [x] Погода → проверенный CSV → чтение этого файла моделью → прогноз.
- [x] Отдельные модели, обученные на реальных данных каждой турбины.
- [x] Скачивание прогноза и точного входного CSV модели.
- [x] OpenAI-объяснение и вопросы по сохранённому на сервере прогнозу.
- [x] Расчётное объяснение при недоступности LLM; сравнение соседних запусков.
- [x] Проверки контрактов, сборка React и один успешный живой тест OpenAI.

В режиме `fixture` погода и координаты синтетические. В `archive` координаты
получены из ссылок организаторов, но историческая пригодность прогнозов погоды
пока не доказана: без проверенного as-issued архива режим заблокирован.
Полная русская локализация ещё не реализована. Мощность нормализована в
диапазоне [0,1]; перевод в МВт/МВт·ч невозможен без подтверждённых данных
о мощности и нормализации.

## Приоритеты

- **P0 — обязательное демо:** полностью русский пользовательский сценарий,
  проверенные границы модулей, понятные ошибки и воспроизводимый запуск.
- **P1 — реальная погода:** подтверждённые координаты и допустимый погодный
  источник вместо заглушек. При отсутствии доступа демо остаётся явно
  демонстрационным; задачу нельзя считать завершённой.
- **P2 — полное решение задания:** исторические прогнозы погоды, пакетный
  февральский расчёт и проверка качества. Это обязательно для полной сдачи,
  даже если презентацию проводят раньше.

## Разработчик A — FastAPI, оркестрация и погода

Владеет `api.py`, `agent.py`, `weather.py`, `contracts.py`, конфигурацией
провайдера и соответствующими тестами. Координирует общие зависимости.

- [ ] **A1 / P0: ошибки и статусы для русского демо.** Согласовать с C стабильные
  коды ошибок и русские сообщения для отсутствующей погоды, неверной даты,
  недоступного сервиса, потерянного после перезапуска прогноза и повреждённого
  CSV. Не показывать пользователю traceback или сырые ответы провайдера.
  **Готово:** каждый сценарий имеет понятное сообщение и действие для повтора;
  HTTP-коды и программные идентификаторы остаются стабильными.
  **Статус:** часть ошибок API переведена на русский без смены кодов/статусов;
  полный пользовательский сценарий и действия для повтора ещё требуют проверки.
- [ ] **A2 / P1: подтвердить метаданные турбин и источник погоды.** Получить
  координаты T1/T2, часовой пояс, доступность почасовых 24/48 часов и права
  доступа к API. Выбрать источник после проверки покрытия; название OpenWeather
  само по себе не гарантирует нужный архив или горизонт.
  **Готово:** источник и ограничения записаны, координаты имеют подтверждение.
  **Статус:** ссылки организаторов подтверждают T1 (43.645150, 78.535604),
  T2 (43.643198, 78.538828); географический часовой пояс Asia/Almaty
  соответствует UTC+5 в январе–феврале 2026 года. Время в исходных CSV и
  высота датчика не подтверждены. Проверены реальные ответы публичного
  Open-Meteo для обеих координат: по 168 часов, включая 48 уникальных целевых
  часов с 2026-01-31T19:00Z по 2026-02-02T18:00Z, конечные м/с и °C;
  обе точки привязаны к сетке (43.620384, 78.47891). Это **ретроспективная
  проверка покрытия**, а не подтверждение доступности прогноза на исторический
  origin. Детали и ограничения: [проверка Open-Meteo](docs/open-meteo-verification.md).
  Независимые свидетельства времени публикации/as-issued ещё отсутствуют;
  A2 не завершена.
- [ ] **A3 / P1: реализовать погодный адаптер.** Сохранить интерфейс
  `fetch_weather`, привести данные к UTC, м/с и °C, проверить полноту часов,
  добавить таймаут, обработку лимита/ошибки API и происхождение данных.
  Ключ хранить только на сервере. Заглушка выбирается явно, без тихого перехода.
  **Готово:** обе турбины проходят цепочку до CSV; неполные и некорректные
  ответы покрыты тестами на сохранённых/поддельных ответах API.
  **Статус:** защищённый адаптер Open-Meteo `archive` реализован за прежним
  `fetch_weather`; `fixture` не подставляется автоматически. Ветер 10 м —
  только прокси для неизвестной высоты исходного датчика; температура 2 м.
  До HTTP требуется проверенный оператором манифест
  `OPEN_METEO_ARCHIVE_MANIFEST` с привязкой к турбине/origin/запуску и
  контрольной суммой полного канонического прогноза; сохраняются также точные
  исходные байты с отдельной суммой. На моках проверена цепочка до реального
  CSV и уже обученной модели для T1/T2 и 24/48 ч. Настоящие as-issued
  свидетельства ещё не получены, поэтому архивное production-применение
  не подтверждено. Схема/ограничения: [CONTRACTS.md](CONTRACTS.md#weather-seam--a-owns-weatherpy).
  Итоговая проверка `dev-a`: **96 Python-тестов**, сборка React и
  `git diff --check` прошли. Проверки провайдера в тестах автономные, на моках.
- [ ] **A4 / P2: историческая погода на момент выпуска.** Для каждого origin
  получать именно доступный тогда прогноз; сохранять исходный ответ, контрольную
  сумму и доказательство времени доступности. Проверять
  `initialized_at <= available_at <= origin`.
  **Готово:** B получает проверенные погодные наборы для всех февральских запусков.
  Фактическая погода, реанализ и прогноз, выпущенный позже origin, недопустимы.

**Важно:** текущий контракт поддерживает `fixture` и `archive`. Если нужен
отдельный прогноз «на сегодня», A согласует добавление режима с B и C во всех
DTO, валидаторах и тестах. Нельзя подставлять сегодняшнюю погоду под январскую
дату или снимать проверки исторической доступности.

## Разработчик B — данные, CSV, прогноз и качество

Владеет `data.py`, `model_input.py`, `model.py`, `scripts/train.py`, будущими
скриптами оценки/пакетного расчёта и соответствующими тестами.

- [ ] **B1 / P0: проверить совместимость реальной погоды и модели.** С A
  подтвердить значение скорости ветра (включая высоту измерения/прогноза),
  температуру, единицы, время и порядок признаков. Описать расхождения между
  измеренными признаками обучения и прогнозными признаками инференса.
  **Готово:** модель по-прежнему читает скачиваемый CSV, выдаёт ровно 24/48
  конечных значений в правильном порядке; ограничения записаны.
- [ ] **B2 / P0: воспроизводимое обучение.** Проверить создание обеих моделей
  из исходных CSV одной документированной командой, идентичность турбины,
  метаданные, исключённые интервалы и соблюдение временной отсечки.
  **Готово:** запуск после удаления только генерируемых артефактов воспроизводит
  рабочее демо; обучение не выполняется внутри HTTP-запроса.
- [ ] **B3 / P1: честная оценка на историческом holdout.** Разделить данные
  хронологически до февраля, сравнить модель с простым baseline, посчитать
  MAE/RMSE отдельно для T1/T2. Не подбирать модель по февралю.
  **Готово:** сохранён отчёт с периодами, числом точек и источником признаков.
  Оценку по измеренной погоде явно отличать от качества прогноза по погодному API.
- [ ] **B4 / P2: пакетный февральский расчёт.** После A4 добавить CLI для
  28 ежедневных origin × 2 турбины × 48 часов = 2 688 строк, включая выход
  горизонта в март. Проверять покрытие, дубликаты, порядок времени и происхождение.
  **Готово:** одна команда создаёт результат и отчёт; пропущенные данные
  перечислены явно, формат сверяется с требованиями организаторов.
- [ ] **B5 / P2: оценка февраля при появлении истины.** Подключить фактическую
  выработку только для итогового сравнения после фиксации прогнозов.
  **Готово:** метрики по турбинам и горизонтам воспроизводимы. Пока истинных
  значений нет, задача заблокирована внешними данными, метрики не выдумываются.

При изменении CSV согласовать версию схемы с A/C и одновременно обновить
writer, reader, признаки обучения и тесты. Существующие имена столбцов не переводить.

## Порядок параллельной работы

1. **Сначала согласовать границы:** A/B — погодные поля, время и координаты;
   A/C — ошибки, режимы и DTO. Записать изменения в CONTRACTS.md до интеграции.
2. **Первый параллельный этап:** A делает A1/A2, B — B1/B2, C — C1/C2/C3.
   C использует текущие fixtures, B проверяет CSV независимо от живого API.
3. **Второй этап:** A подключает A3, B делает B3, C завершает C4/C5.
   Если источник заблокирован, продолжать остальные задачи и явно фиксировать блокер.
4. **Совместная сборка:** A запускает API и собирает совместимые изменения,
   B сверяет скачанный CSV и модель, C проводит русский сценарий.
5. **Полная сдача:** A4 → B4 → B5 при наличии истины. Не смешивать этот статус
   с готовностью презентационного демо.

Каждый коммит — небольшой законченный шаг с ID задачи; регулярно коммитить
работающий результат. Общие файлы и зависимости меняет согласованный владелец.
Не добавлять авторизацию, БД, очереди, иерархию агентов или второго LLM-провайдера
до закрытия обязательного сценария.
